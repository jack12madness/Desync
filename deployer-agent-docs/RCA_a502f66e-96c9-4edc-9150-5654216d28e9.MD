# RCA — Desync (desync.website): "code accepted but session couldn't start" (/portal/me 401)

## Verdict
This is a **frontend code bug**, not an infra / multi-pod / JWT_SECRET issue. The multi-pod-secret-mismatch hypothesis is **disproven by direct evidence**. No pod drain/restart is warranted and none would fix it.

## Actual root cause (frontend)
File `frontend/src/lib/api.js` registers a global axios request interceptor on the shared `api` instance:
```js
api.interceptors.request.use((config) => {
  const token = localStorage.getItem("void_admin_token");
  if (token) { config.headers.Authorization = `Bearer ${token}`; }
  return config;
});
```
This **unconditionally overwrites** the `Authorization` header on every request when an admin session (`void_admin_token`) exists in localStorage.

`frontend/src/pages/CustomerPortal.jsx` (`loadPortal`) explicitly calls:
```js
api.get("/portal/me", { headers: { Authorization: `Bearer ${tok}` } }); // tok = buyer_lookup token
```
The interceptor runs after this and **replaces the buyer token with the admin token**.

Backend `server.py` `_buyer_email()` (used by `/portal/me`, `/portal/gen/*`, `/portal/reviews`) requires:
```python
if payload.get("type") != "buyer_lookup": raise HTTPException(401, "Verification required")
```
An admin token has `type == "admin_access"` → **persistent 401**, and the frontend's ~1.5s retry re-sends the same admin-overwritten header → 401 again → "Your code was accepted but the session couldn't start."

Note: `POST /api/orders/lookup/verify` takes no auth header, so it always returns 200 (token minted) — exactly the observed failure staging.

## Proof
- Same-pod verify(200)→/portal/me(401) pairs on both h8qgs and z78hv (fetch_app_logs, per-pod, active run).
- Both pods on the current active image, restart_count 0, no stray pods (get_pod_events).
- Reproduced the axios behavior in an isolated sandbox with a single interceptor + mock adapter: request built with `Authorization: Bearer BUYER_TOKEN_buyer_lookup`, but **SENT as `Bearer ADMIN_TOKEN_admin_access`** — the interceptor wins.

## Who this affects
Any browser/origin that has logged into the admin dashboard (`void_admin_token` present) — e.g. the owner testing the portal — hits this 100% of the time. Pure customers who never logged into admin are NOT affected by this specific overwrite; their historical "code invalid/expired" reports (if any) would be a separate matter (genuinely expired OTPs / the 60s resend 429), not this bug.

## Suggested fix (Code — E1; no deployer/infra action)
In `frontend/src/lib/api.js`, do not clobber an Authorization header the caller already set. Minimal fix:
```js
api.interceptors.request.use((config) => {
  if (!config.headers?.Authorization) {
    const token = localStorage.getItem("void_admin_token");
    if (token) config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});
```
Better/robust: use a separate axios instance (or no interceptor) for the customer-portal calls, or skip attaching the admin token for `/portal/*` and `/orders/lookup/*` routes. After the code change, redeploy.

## Not the cause
- No multi-pod JWT_SECRET mismatch (same-pod failures; single env snapshot per run).
- No stray/old pod; both replicas on the current active image.
- No manifest/tier/secret/DNS issue.
